# Systems & Automation Division Governance Policy

**Owner:** Systems & Automation Division (all agents: Reliability & Monitoring, and any future agent under System Architecture, Software Development, AI Automation, Integration & APIs, Databases & Infrastructure, Security & Performance, Tools & Internal Systems)
**Authority:** Subordinate to the Constitution and to `governance/policies/self_healing_governance.md`. This policy may not be amended by any AI agent — only by Mohamed.
**Written by:** Claude, at Mohamed's explicit request, 2026-08-06 — this division's agents are the first in AI_EMPIRE with the standing ability to kill and restart real running processes, which is meaningfully more consequential than any read-only Audit check and needs its own explicit rules before more agents are added here.

## Core Principle

**Infrastructure Trust Principle:** Systems & Automation agents keep the rest of AI_EMPIRE running — they do not get to change what it does. Every agent in this division is scoped to a named, narrow set of processes and tables it is allowed to touch, declared in `agent_registry.metadata` before it is ever run. Anything outside that declared scope is out of reach by construction, not by convention.

## The 10 Rules

1. **Declared Scope Only — meant to be enforced by the database, not just by code.** An agent may act only on the specific services/processes/tables listed in its own `agent_registry` row. No agent in this division gets implicit or broad system access "because it's the systems division." The intended mechanism: Reliability & Monitoring connects to AI_EMPIRE's own database as a dedicated `ai_empire_systems_agent` Postgres role (`infrastructure/database/migrations/0009_systems_agent_scoped_role.sql`, `shared/systems_db_connector.py`), scoped to only SELECT/INSERT/UPDATE `circuit_breakers` and SELECT/INSERT `audit_vault` — nothing else, at the database level, regardless of what the application code does. **Status as of 2026-08-06: this role and connector are fully built but NOT currently in use.** Live testing found Supabase's Supavisor pooler rejects this role's connections before they ever reach Postgres (confirmed via Postgres's own logs showing zero trace of the failed attempts, ruling out a credentials mistake) — a real platform-level issue, still unresolved, most likely because Supavisor needs custom roles registered with it through some mechanism beyond a plain `CREATE ROLE` in SQL. Mohamed's explicit, informed choice: rather than block the agent entirely on this unresolved issue, `agents/systems/reliability_monitor.py` currently uses `shared/db.py`'s `get_client()` — the same all-powerful `service_role` key every other agent in the project already uses — same access level as everything else in AI_EMPIRE today, not a new or unusual exposure, but also not the real enforcement this rule is meant to provide. This is tracked as open follow-up work, not silently abandoned. A new capability (e.g. a future Software Development or Databases & Infrastructure agent) should still get its own scope declaration reviewed against this policy AND attempt its own equally-scoped database role before falling back to the shared credential the same way.
2. **Data-Tier Services Are Never Auto-Restarted.** Supabase (or any future database service) is detection-and-alert only, always. A mid-transaction restart risks real data corruption — no exception, no override, not even at Mohamed's remote instruction without him being present to verify state afterward.
3. **Out-of-Reach Services Are Detection-Only.** A service this machine cannot actually control (e.g. Ollama, which runs on a separate Mac with no remote-exec access configured) is never assumed remediable. The agent may only detect and alert — inventing a "fix" for something it can't touch is worse than doing nothing.
4. **One Remediation Attempt Per Incident.** Auto-restart fires at most once per failure episode. If the service is still unhealthy afterward, the agent stops, moves to `fallback` state, and waits for a human or for the service to recover on its own — never retries in a loop. Restart-thrashing a failing service is itself an outage.
5. **Every State Change Is Logged Immutably.** Every transition a service's circuit breaker makes (not every health check — only actual changes) is written to `audit_vault` with the old state, new state, and a reference to this policy. No silent state changes.
6. **Every Autonomous Action Alerts.** A restart attempt, a circuit opening, or a fallback triggers a real-time Telegram message to Mohamed. Never a silent fix — even a successful one.
7. **Division Boundary.** No Systems & Automation agent may write to another division's tables, `agent_registry`, `routing_logs`, or any table outside what it explicitly needs (Reliability & Monitoring: `circuit_breakers` and `audit_vault` only — never `memory_experience`/`memory_knowledge` writes framed as anything but its own operational log).
8. **The Cybersecurity Lab Is Air-Gapped From Production Credentials.** Any lab environment (VMs, containers, security tooling) built under this division's "Tools & Internal Systems" pillar must never have access to real AI_EMPIRE or Fixera credentials — `.env`, service-role keys, OAuth tokens, connector access. Lab tooling gets synthetic data and its own isolated config, full stop. This is a hard boundary, not a best-effort one, given the whole point of the lab is practicing offensive security techniques.
9. **Anything Beyond "Restart a Known-Safe Local Process" Needs the Two-Agent Rule.** Restarting n8n or a division's own FastAPI server (both stateless, both already fully reversible by re-running the same start command) is the ceiling of what any agent in this division may do unsupervised. Anything past that — modifying code, changing infrastructure configuration, installing software, touching a database schema — falls under `self_healing_governance.md`'s existing Two-Agent Rule and Rule 8 (risk-based approval): proposed, never auto-applied, until a real risk classifier exists.
10. **New Agent = New Governance Line Item.** Before any future agent is built under this division's other 6 pillars (System Architecture, Software Development, AI Automation, Integration & APIs, Databases & Infrastructure, Security & Performance), its specific action scope gets added to this document and reviewed with Mohamed first — this policy is meant to grow with the division, not be written once and left behind it.

## Current implementation status (v0.1, 2026-08-06; Workflow Builder added 2026-08-10)

**Workflow Builder Agent** (`agents/systems/workflow_builder.py`, AI Automation pillar — the division's first agent outside Reliability & Monitoring) complies with Rule 9 by construction: its only action is writing a *new* n8n workflow JSON file to `infrastructure/n8n/` for Mohamed to review and manually import — it never connects to a live n8n instance, never imports or activates a workflow, and never modifies or overwrites an existing workflow file (a name collision is refused, not resolved automatically). This is "proposed, never auto-applied" without needing a runtime Two-Agent Rule check, because the human review step *is* Mohamed choosing to import the file himself, same as every one of the 16 existing workflows already required. An Ollama judgment call (via `shared/models/generate.py`'s `chat()`) parses a plain-language description into structured parameters (division, trigger type/value, endpoint path, workflow name), validated against the known division→port map; a separate, deterministic Python template then builds the exact JSON matching the established two-node (`scheduleTrigger` → `httpRequest`) pattern every existing workflow uses — the model only interprets intent, it never writes the JSON directly, so a bad or ambiguous description fails closed (`{"ok": False, "reason": ...}`) rather than producing malformed or hallucinated workflow structure.

**Reliability & Monitoring Agent** (`agents/systems/reliability_monitor.py`) is the division's original agent. It complies with Rules 2–9 by construction: it restarts only `n8n` and each division's own FastAPI server (never Supabase, never Ollama), makes exactly one restart attempt per incident before moving to `fallback`, and logs every state change to `audit_vault`, alerting via Telegram on every change. **Rule 1's database-level enforcement is not yet live** — see Rule 1's own status note above for the full detail: the scoped `ai_empire_systems_agent` role and its connector (`shared/systems_db_connector.py`) are fully built but blocked on an unresolved Supavisor pooler issue, so the agent currently runs on the same blanket service-role key as everything else in the project. One more honest gap in the same direction: `agents/systems/_telegram.py`'s failure-logging path also writes to `memory_experience` via that broad client, matching the pattern every other division's `_telegram.py` already uses for that same low-stakes, informational-only path. Real least-privilege enforcement for this division — and the equivalent for every other division's agents — is tracked as genuine follow-up work, not something to claim as done. No cybersecurity lab or any of the other 6 pillars has been built yet — Rule 8 and Rule 10 are written ahead of that work specifically so it starts from a real boundary instead of getting one retrofitted later.
